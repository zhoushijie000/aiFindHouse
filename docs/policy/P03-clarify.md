# P03 · 政策条件补充追问

> 本文是**建议输出契约**。原文要求判断信息是否充分，但没有给出政策最小查询范围的固定字段组合；本节点不得把建议当成既定 API 或强制业务规则。

## 节点职责

在系统判定现有条件不能执行有效查询时，生成一次最少必要追问。避免把所有政策查询都变成填写区域、类型、时间三项的表单。

## 触发

P02 输出经系统查询范围规则校验后，得到 `query_allowed=false`，并提供明确的缺失项或歧义。已满足规则则绕过本节点，直接查询政策库。

## 输入

- `extracted_filters`：已确认查询条件。
- `scope_validation`：系统校验结果及真实缺失项。
- `ambiguous_references`：如“刚才那个”对应多个政策。
- `available_choices`：业务字典或已查得政策提供的有效候选。
- `recent_turns`：避免重复询问已经回答的内容。

## AI 输出 JSON 示例

```json
{
  "node_id": "P03",
  "reply": "你想了解哪一项政策？可以点选刚才结果中的政策，再让我帮你查看。",
  "clarify_fields": ["policy_id"],
  "choices": [
    {"label": "示意政策 A（非真实政策）", "value": "demo-policy-a"},
    {"label": "示意政策 B（非真实政策）", "value": "demo-policy-b"}
  ],
  "preserve_existing_filters": true,
  "next_node": "WAIT_USER_THEN_P02"
}
```

示意场景：已有两条结果，用户说“解读刚才那个”，系统无法确定政策引用。示例选择项必须来自实际会话结果；生产中不得使用示意 ID。

## 字段说明

| 字段 | 说明 |
| --- | --- |
| `reply` | 简短追问，只覆盖真正阻塞查询的内容。 |
| `clarify_fields` | 本次要求补充或确认的条件。 |
| `choices` | 可点击候选，仅来自输入中的有效数据；没有有效候选时为空。 |
| `preserve_existing_filters` | 提示系统保留已经确认的政策条件。 |
| `next_node` | 等待用户后回到 P02，重新合并和校验条件。 |

## 约束

1. 最小查询范围由服务端配置规则判断，AI 只组织追问文案，不自行添加强制字段。
2. “成都全市最新购房政策”不必追问区域、政策类型；泛全市查询在查询接口支持时可以直接查。
3. “现在有什么政策”如业务规则允许默认成都全市，应明确采用全市范围并直接查询；如规则尚未配置，不把任意区县作为默认值。
4. 一轮优先解决一个关键歧义；不索取与本次查询无关的预算、收入、证件等信息。
5. 追问阶段不输出“当地有某补贴”“你符合某资格”等未经业务数据支持的事实。

## 失败处理

- 用户未回答所问但提供新问题：返回 P01 重新判意图，保留会话历史。
- 多轮仍无法消歧：提供业务范围说明及可直接查询的全市政策入口，入口必须符合服务端能力；不编造选项。
- AI 异常：显示标准 AI 异常提示，保留用户已输入条件与可重试状态。

## 验收样例

| 场景 | 预期 |
| --- | --- |
| “成都全市最新政策”，系统允许全市查询 | 跳过 P03，直接查询。 |
| “哪个人才政策？”存在两个可引用条目 | 给出真实条目选择，确认政策 ID。 |
| 已有区域，系统要求补齐无法映射的类型 | 只问类型，不重复问区域。 |
| 用户说“换成锦江区吧” | 回 P02 更新区域并重查充分性。 |

## 可复用提示词

根据系统提供的缺失项或歧义生成一次简短追问。不要自行增加必填项；已允许的全市最新查询无需追问。候选值必须取自输入，保留已确认条件。
