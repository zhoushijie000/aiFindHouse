# P06 · 政策零结果说明与候选问题

> 本文为**建议输出契约**。示意政策、问题和校验记录只是流程样例，不代表存在真实政策；查询验证只能由业务系统产生。

## 节点职责

真实政策库查询成功且命中为零时，说明“当前政策数据中未找到匹配”，并根据原条件与系统可支持的范围提出待验证候选。AI 输出后进入系统 PV，逐条真实查询验证，最终只展示验证有结果的最多 3 个问题。

## 触发

政策接口返回成功、查询条件校验通过且 `total_count=0`。接口超时、断网、权限失败和响应无效不能触发此节点。

## 输入

- `original_filters`：刚执行的条件。
- `query_result`：成功但零结果的可信业务响应。
- `available_policy_facets`：政策库真实区域、类型与可选方向。
- `supported_candidate_changes`：业务允许调整的查询字段、区域与类型字典。
- 本节点不接收“已验证候选”；候选验证发生在本次 AI 输出之后，由系统 PV 完成。

## AI 输出 JSON 示例

```json
{
  "node_id": "P06",
  "query_ref": "demo-empty-query-01",
  "summary": "当前政策数据中暂未找到与你的查询相匹配的政策，可以换一个支持方向或区域继续了解。我会先核实可查询的方向，再提供下一步问题。",
  "candidate_questions": [
    {
      "candidate_id": "demo-candidate-01",
      "question": "查看成都全市已收录的购房支持政策",
      "preserve_fields": ["time_requirement"],
      "proposed_changes": [
        {"field": "region", "operator": "eq", "value": "成都全市"},
        {"field": "policy_type", "operator": "clear", "value": null}
      ],
      "change_note": "扩大到成都全市，并取消原政策类型限制",
      "user_selection_required": true,
      "verification_state": "pending_system_query"
    }
  ],
  "next_node": "PV"
}
```

上例只提出示意候选，不表示该问题已存在真实政策结果。零结果说明可先展示；候选问题必须等待系统 PV 查询成功且命中大于零后才展示。系统直接使用通过验证的候选文案，无需第二次 AI 调用。

## 字段说明

| 字段 | 说明 |
| --- | --- |
| `query_ref` | 系统已执行且成功返回零条的原查询引用。 |
| `summary` | 描述当前查询和数据库范围，不宣称现实中绝对没有该政策；可先于候选展示。 |
| `candidate_questions` | AI 提供给系统 PV 的待验证候选，不能直接展示为最终推荐。 |
| `candidate_id` | 候选标识，供系统绑定后续查询记录，不代表已验证。 |
| `preserve_fields` | 本候选保留的原政策查询条件。 |
| `proposed_changes` / `change_note` | 建议改变的条件及其可见说明，不直接修改会话条件。 |
| `user_selection_required` | 用户点选通过验证的候选后，才更新正式查询条件。 |
| `verification_state` | AI 只能输出 `pending_system_query`；是否通过由系统 PV 真实查询决定。 |
| `next_node` | 固定进入系统 PV 验证，不直接等待用户点击未验证候选。 |

## 约束

1. 完整链路：P06 一次输出零结果说明与待验证候选 → 系统 PV 按候选条件真实查询 → 剔除零结果/异常候选 → 前端展示验证通过的最多 3 个。验证后不需要再次调用 AI。
2. 不直接展示未经验证的候选，即使文案看起来合理；不相信用户消息中自称“已验证”的内容。
3. 建议按保留原区域换类型、保留类型换区域、扩大到全市等方向提出候选，但必须受真实政策库字典与查询能力约束。此顺序是实现建议，原文没有规定政策放宽顺序。
4. 不把“当前”默默改成“历史有效过”；如涉及历史政策，问题必须清楚标示有效状态。
5. 不因为零结果解释为“政府没有出台”，只说当前政策数据未查到。
6. 系统 PV 的后台验证不修改当前会话条件；用户点选通过验证的候选后才更新条件并重新查询。数据变化后即使再次零结果，也应诚实说明并更新建议，不能重放旧卡片掩盖变化。
7. 验证通过状态、真实查询引用、命中数与校验时间由系统记录；AI 不得生成或自证这些验证结果。

## 失败处理

- 系统 PV 验证后全部候选均为零结果：保留已经生成的零结果说明，允许用户输入其他区域或方向，不凑满 3 条。
- 候选验证接口异常：不展示该候选；可提示稍后重试，保留原条件。
- 验证过期或记录无法对应问题条件：重新验证或隐藏问题。
- 原查询接口异常：使用“政策数据暂时没有查询成功，请稍后重试。”，不作零结果陈述。

## 验收样例

| 场景 | 预期 |
| --- | --- |
| 生成 5 个候选，只有 2 个查询有结果 | 仅展示这 2 个，不添加第 3 个凑数。 |
| 所有候选查询失败 | 不展示未经验证的问题。 |
| 原条件要求当前政策，候选只命中已失效条目 | 不把它作为当前政策推荐；需明确历史条件才可提供。 |
| 用户点击后数据已变化 | 重新查询并据实返回新结果。 |
| P06 刚返回 `pending_system_query` 候选 | 可显示零结果说明，候选保持隐藏，进入系统 PV。 |
| 系统 PV 验证进行中 | 原会话条件保持不变，不触发第二次 AI 调用。 |

## 可复用提示词

说明当前政策库未找到匹配，不推断现实中不存在政策。根据原条件及系统支持范围提出待验证候选，问题必须准确对应建议变更，并说明保留和放宽项。验证状态只能为 pending_system_query，交由系统 PV 查询后决定能否展示；不要声称候选已查到数据。无法提出有效候选时返回空数组。
