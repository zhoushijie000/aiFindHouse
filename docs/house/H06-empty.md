# H06 · 零结果说明与候选问题

> 本文为建议的 AI 输出契约，字段名并非原需求文档已有 API。JSON 仅为示意。候选问题并不意味着已存在真实结果。

## 节点职责与触发

楼盘业务接口成功、匹配数确实为 0 时，说明本轮没有匹配结果，并提出可供系统验证的调整方向。系统逐条查询验证有结果后，才允许前端显示最多 3 个推荐问题。

## 输入

- 原始用户诉求、原硬性条件与本轮实际查询条件。
- 成功且为零的本轮查询结果。
- 系统可支持的候选变更范围；如二次生成文案，需传入已经验证的候选及查询引用。

## AI 输出 JSON 示例

示意输入：用户查询青羊区 5000 万元左右，近似范围已按业务规则确认，本次查询无匹配。

```json
{
  "node_id": "H06",
  "query_ref": "demo_empty_query_01",
  "summary": "暂未找到完全符合当前条件的在售新房。可以保留区域调整预算，或保留预算换个区域继续找；我会先核实可查询的方向，再提供下一步问题。",
  "candidate_questions": [
    {
      "candidate_id": "demo_candidate_01",
      "question": "青羊区3000万以上有哪些楼盘？",
      "preserve_fields": ["region"],
      "proposed_changes": [
        { "field": "total_price_wan", "operator": "gte", "value": 3000 }
      ],
      "user_selection_required": true,
      "verification_state": "pending_system_query"
    }
  ]
}
```

## 字段说明

| 字段 | 含义 |
| --- | --- |
| `summary` | 仅说明本轮无匹配；不能把零结果推断为市场不存在该价格段 |
| `candidate_questions` | AI 提供给系统的待验证候选，非可直接显示的最终推荐 |
| `preserve_fields` | 本方案保留的原条件 |
| `proposed_changes` | 明示需要改变的条件，不能悄悄修改会话条件 |
| `user_selection_required` | 调整硬条件必须由用户选择候选后才用于正式查询 |
| `verification_state` | AI 只能给 pending_system_query；通过与否由系统填写 |

## 输出约束与系统衔接

1. 候选优先级沿用原文：保留区域调预算 → 保留预算调区域 → 保留购房档次扩大区域 → 放宽全部限制。
2. 系统按候选真实条件查询，记录可核验的查询标识和大于 0 的匹配数；失败、零结果、未经验证的候选一律隐藏。
3. 前端只展示系统验证通过的前 3 个；不足 3 个不补造。全部失败时保留说明和手动修改入口。
4. 用户点击候选后才更新相应条件并重新查询；提示改了哪些条件。后台验证不会修改当前会话筛选条件。
5. 实时数据变化可能使点击后变成零结果，应按新的实际查询继续处理，不能复用旧结果假装有房。

## 失败处理

主查询异常不进入本节点。候选验证接口失败时不展示该问题，也不谎称验证为零。原会话条件和零结果说明保留，允许用户手动修改或重试。

## 验收样例

| 情况 | 预期 |
| --- | --- |
| AI 生成3个候选，只有1个验证有数据 | 只展示1个 |
| 所有候选均为0或失败 | 不显示虚构推荐问题 |
| 提出降低预算的候选，但用户未点击 | 原预算保持不变 |
| 主查询超时 | 走接口异常，不能走零结果 |
